# ARA — البنية المعمارية

## الطبقات
```
Kotlin / Compose ─ ChatScreen · ModelsScreen · SkillsScreen · SettingsScreen
   │  CoreBridge (Dispatchers.IO)      HostActions (Intents — قائمة مسموحة ثابتة)
   │  UniFFI: AraCore + TextListener/ProgressListener/CancelHandle
   ▼
ara-ffi ── AraCore (حالة التطبيق) + conversations (JSON محلي)
   ├─ ara-coordinator   توجيه المهارات → RAG → سياق محدود → توليد → أدوات → إجابة
   ├─ ara-search        SQLite FTS5 + تطبيع عربي + تقاطع لهجات/لغات + ذاكرة المستخدم (index.db)
   ├─ ara-cloud         API Hub (OpenAI-compatible SSE) + Privacy Shield
   │     ├─ ara-inference (+llama.cpp عبر llama-cpp-2، CPU)
   │     └─ ara-tools     manifests · schema · policy · parse · builtin · skills
   ├─ ara-model-manager  تنزيل مستأنف · SHA-256 · حد مساحة · قفل · حذف آمن
   ├─ ara-crypto         تشفير ظرفي AES-256-GCM (T1.8) · توقيع/تحقق Ed25519 (T2.2b) — ADR-018
   ├─ ara-smarthome      عميل Home Assistant REST (ping/states/call_service) — ADR-020، غير موصول بـToolRegistry بعد
   ├─ ara-backup         تصدير/استيراد مشفّر بعبارة مرور للمجلد المحلي (بدون models/) — ADR-021، غير موصول بواجهة Kotlin بعد
   ├─ ara-model-selector استبعاد + ترتيب بطبقات + معايرة بالقياس
   ├─ ara-model-registry كتالوج JSON (core/catalog/models.json)
   ├─ ara-device-profiler /proc/meminfo · statvfs · /proc/self/status
   └─ ara-core-api       أخطاء · أحداث · إلغاء
ara-cli: أداة مطور تشغّل نفس النواة (profile/models/download/bench/chat/agent)
```
منطق الأعمال كله في Rust. Kotlin يجمع حقائق المنصة وينفذ Intents التي وافقت عليها النواة.

## قرارات معمارية

### ADR-001: UniFFI بدل JNI يدوي
مُختبر: ترجمة الربط المولّد داخل التطبيق، 5 اختبارات JVM عبر JNA. اكتُشف تعارض حقل `message` مع `Throwable.message` ⇒ حقول الأخطاء اسمها `detail`.

### ADR-002: JSON عبر الجسر للهياكل المركبة
الكائن `AraCore` مطبوع النوع، والهياكل الكبيرة (قائمة النماذج، نتيجة الدور) JSON مملوكة لـ serde. يُعاد التقييم عند استقرار الـ schemas.

### ADR-003: اختيار النموذج
- الاستبعاد: الرام المتاحة × 0.85 − 512MB؛ التقدير = حجم الملف + KV (من معمارية النموذج: طبقات × رؤوس KV × بُعد الرأس × 2 × 2 بايت) × السياق + 256MB.
- السرعة المقدّرة = عرض النطاق ÷ حجم الملف (التوليد على CPU محدود بالذاكرة). الافتراضي 6 GB/s ثم يُعايَر بوسيط القياسات الفعلية.
- الترتيب بطبقات قابلة للشرح؛ داخل الطبقة: جودة (log المعاملات، خصم بسيط لـ 4-bit) وسرعة على مقياس لوغاريتمي.

### ADR-004: كتالوج النماذج
فقط ناشرون رسميون وتراخيص Apache-2.0/MIT وملف واحد. مستبعد عمدًا: Qwen2.5-3B (رخصة بحثية)، Gemma (شروط خاصة/مقيد)، Phi-4-mini (رفع طرف ثالث)، 7B (ملفات مقسمة). يُولّد بـ `scripts/gen_catalog.py` من بيانات Hugging Face API (الحجم وsha256 من LFS).

### ADR-005: llama.cpp عبر `llama-cpp-2` 0.1.161
مُثبّت الإصدار. على Android: libc++ ثابت ⇒ `.so` واحد يعتمد فقط على libc/libm/libdl (~10MB لكل معمارية). سياق جديد لكل طلب (تبسيط للـ lifetimes)؛ إعادة استخدام KV مؤجلة.

### ADR-006: المهارات والأدوات
- الأداة تعلن: schema صارم (رفض المفاتيح المجهولة، حدود الطول بالحروف)، صلاحيات، نوع الأثر (None/Reversible/External)، Core/Host، مهلة، حد مخرجات، حد معدل.
- `dispatch` نقطة الدخول الوحيدة: tool مجهول ⇒ رفض؛ schema ⇒ precheck دلالي (https فقط، أرقام هواتف، تواريخ) ⇒ صلاحية المستخدم ⇒ تأكيد ⇒ حد المعدل ⇒ تنفيذ.
- **أي أثر External يطلب تأكيدًا دائمًا** حتى لو كانت الصلاحية "مسموح".
- لا أداة Shell أو تنفيذ كود.
- **الموجّه (router)**: كلمات مفتاحية عربي/مصري/إنجليزي تختار المهارات ذات الصلة فقط ⇒ الـ prompt نزل من ~1800 إلى ~550 token.
- صيغة الأدوات مطابقة حرفيًا لقالب Qwen الرسمي (التجربة أظهرت أن صياغة مختلفة جعلت 1.5B يرفض المهام).

### ADR-007: واتساب وتيليجرام والسوشيال
- الآن: Intents رسمية تفتح التطبيق بالمحتوى جاهزًا، والمستخدم يضغط إرسال. مجاني، لا مفاتيح، لا مخالفة لشروط الخدمة، لا إرسال خفي.
- لا نستخدم Accessibility لأتمتة واتساب (مخالف للشروط وخطر أمني).
- لاحقًا (G9): Telegram Bot API للتحكم عن بُعد (خادم + توكن، تحقق الهوية على الخادم)، WhatsApp Business Cloud API للحسابات التجارية فقط.

### ADR-008: الرام والمساحة
- نموذج واحد مقيم؛ تفريغه عند `onTrimMemory(BACKGROUND)` أو تبديل النموذج.
- حجم السياق قابل للضبط (2K/4K/8K) ويؤثر مباشرة على KV cache.
- حد مساحة للنماذج يختاره المستخدم + 1GB مساحة حرة دائمًا.
- الأوزان mmap (llama.cpp) فلا تُنسخ في الذاكرة.

### ADR-009: إعادة استخدام KV cache
السياق يعيش مع النموذج (`self_cell` بدل `unsafe`). في كل طلب: أطول بادئة مشتركة من الـ tokens تبقى، ويُحذف الباقي بـ `clear_kv_cache_seq`، ويُقيَّم الذيل الجديد فقط. إن فشل الحذف الجزئي (بعض المعماريات) ⇒ مسح كامل. أي خطأ ⇒ مسح الكاش حتى لا يبقى غير متسق.

### ADR-010: البحث والذاكرة
- SQLite (rusqlite 0.41.1 bundled) في ملف واحد `index.db`: documents/chunks + FTS5 contentless على نص مُطبّع.
- التطبيع العربي نفسه للفهرسة والاستعلام: حذف التشكيل والتطويل، توحيد أ/إ/آ/ٱ→ا، ى→ي، ة→ه، ؤ→و، ئ→ي، أرقام عربية→لاتينية.
- كل كلمة في الاستعلام بين علامتي تنصيص ⇒ لا حقن لصيغة FTS5.
- المقاطع ~800 حرف مع تداخل؛ رقم السطر في الاستشهاد هو السطر الأكثر تطابقًا داخل المقطع.
- RAG حتمي: عند توجيه مهارة «ملفاتي» تبحث النواة أولًا (بنفس فحص الصلاحيات) وتضع المقاطع مع مصادرها قبل السؤال، ولا تُحفظ في المحادثة.
- الذاكرة: لا حفظ تلقائي؛ أداة `remember` تحتاج صلاحية + تأكيد، والمستخدم يضيف/يعطّل/يحذف. الذكريات المفعلة تُضاف للـ system prompt بحد 1200 حرف.
- أنواع الأدوات: Core (حساب نقي) / Host (Intents في Kotlin) / Service (حالة داخل النواة: البحث والذاكرة).

### ADR-011: الأوضاع المتخصصة (Personas)
نص الوضع موثوق (first-party) ولا يوسّع صلاحيات أي أداة. الوضع يضيف مهارات دائمة لكن **لا يفرض البحث في الملفات** (البحث الحتمي يحدث فقط إن سأل المستخدم عن ملفاته؛ التجربة أظهرت أن فرضه أفسد الإجابات). صياغة وضع الأمن إيجابية ومحددة لأن الصياغة المليئة بالمحظورات جعلت النموذج الصغير يرفض مراجعة كود عادي.

### ADR-013: تحسين العربية بلا تدريب (crosswalk + aliases مُتعلّمة من المستخدم)
**القرار:** لا نموذج يُدرَّب/يُضبَط (fine-tune) لتحسين فهم اللهجة. السبب: التدريب يحتاج GPU ومجموعة بيانات ومعايرة مستمرة، والنتيجة لسه لازم تضبط في رام الهاتف — تكلفة وخطر على "صحة الجهاز" بدون ضرورة، بينما مشكلة الاسترجاع (لا التوليد) تُحل برُكّة مرادفات.
- `core/lexicon/ar_crosswalk.json` — جدول ثابت (مصري/فصحى/إنجليزي، مثل «الذكاء الاصطناعي التوليدي» ↔ «Generative AI») يُعدَّل كبيانات بدون إعادة تدريب أو حتى إعادة بناء المنطق. يُحمَّل مرة واحدة (`OnceLock`) بحجم كيلوبايتات قليلة.
- `learned_aliases` في `index.db`: تعلّم من تفاعل المستخدم نفسه — **لا كتابة تلقائية أبدًا** (نفس قاعدة الذاكرة)، فقط عند تأكيد صريح (`confirm_alias`). محدود بسقف صارم `MAX_LEARNED_ALIASES = 2000` صفًا مع إخلاء الأقل استخدامًا/الأقدم ⇒ لا يمكن أن ينمو التخزين أو زمن الاستعلام بلا حدود.
- التوسيع عند البحث فقط (لا يُغيَّر الفهرس): كل كلمة/عبارة في الاستعلام تُقارَن بالعبارة كاملة (مطابقة بحدود كلمة، لا تطابق جزئي داخل كلمة أخرى) ثم تُضاف مرادفاتها OR، بحد أقصى `MAX_QUERY_TERMS = 24` لكل استعلام. تكلفة المعالج: مسح خطي لعشرات المجموعات القصيرة — لا نموذج يُشغَّل، فلا أثر يُذكر على الرام أو البطارية أو الحرارة.
- البحث الدلالي بتضمينات (T1.2) يبقى مخططًا ومنفصلاً: عند تنفيذه سيستخدم نموذج تضمين **جاهز ومُدرَّب مسبقًا** (لن نُدرّب نحن نموذجًا) ويُفعَّل فقط حسب فئة الجهاز (`ara-device-profiler`)، مع سقوط آمن (fallback) للبحث النصي وحده على الأجهزة الضعيفة.
- مُختبر: `core/crates/ara-search/src/lexicon.rs` و `lib.rs` (20 اختبارًا تشمل تقاطع لهجة/لغة، تعلّم عند التأكيد فقط، وثبات السقف `MAX_LEARNED_ALIASES` بعد تجاوزه).
- **إصلاح (2026-11-25، اكتُشف أثناء بناء T1.3):** اختيار "أفضل سطر داخل المقطع" للاستشهاد كان يحسب التداخل بكلمات الاستعلام *الحرفية* فقط، لا الموسَّعة. نتيجته: نتيجة وصلت فقط عبر تقاطع لهجات/لغات (الاستعلام لا يطابق المستند حرفيًا بأي كلمة) كانت تُستشهَد بسطر عشوائي (آخر سطر، بسبب كسر التعادل) بدل السطر الذي طابق فعليًا. الإصلاح: الحساب الآن يستخدم قائمة الكلمات الموسَّعة نفسها. اختبار `crosswalk_driven_hits_cite_the_right_line_not_just_the_right_document` يثبت الانحدار (فشل فعليًا بالمنطق القديم قبل الإصلاح، نجح بعده) — ملاحظة مهمة اكتُشفت بالتجربة: المرادفات بلا "ال" (مثل `مهمه`) لا تطابق نفس الكلمة بأل التعريف (`المهمه`) على مستوى FTS tokenizer (لا تدخل اشتقاق/تجريد)، فبعض أمثلة التقاطع الحقيقية تحتاج صياغة تتجنّب "ال" على الكلمة المستهدَفة — قيد معروف، لا حل كامل له الآن.

### ADR-014: استخراج PDF واستشهاد بالصفحة (T1.1)
- `pdf-extract` (Rust خالص، MIT) يستخرج النص صفحة بصفحة (`extract_text_from_mem_by_pages`) — بلا مكتبة native خارجية، بلا OCR (ملف PDF ممسوح كصورة بلا طبقة نص يُرفض بوضوح، لا يُفهرَس فاضيًا).
- `documents.page_starts` (JSON، عمود اختياري NULL لغير PDF) يخزّن أول سطر لكل صفحة في النص المُستخرَج المُجمَّع؛ `extract::page_for_line` يحوّل أي سطر عام لرقم صفحة بمسح خطي على عدد صفحات الملف (عشرات عادة) — لا فهرس إضافي ولا تكلفة تُذكر.
- الاستشهاد في `search()` يرجّح الصفحة: مستند PDF ⇒ `"name.pdf:page 3"`، مستند نصي ⇒ `"name.txt:42"` (كما كان). التعديل في `ara-coordinator::IndexServices` فقط؛ لا تغيير على عقد الأداة.
- مُختبر بملفات PDF حقيقية مبنية بـ`lopdf` (ليست بايتات مُلفَّقة): استخراج نص 3 صفحات، تتبّع حدود الصفحات، رفض PDF بلا نص، واستشهاد صحيح بالصفحة عبر `SearchIndex` كاملة (5 اختبارات جديدة في `extract.rs` + `lib.rs`).
- لم يُقَس بعد: Recall@K/MRR على مجموعة 20 سؤالًا (معيار القبول الكامل لـ T1.1 في `ROADMAP_TASKS.md`) — هذا يحتاج مجموعة تقييم PDF حقيقية لم تُجهَّز بعد.

### ADR-015: Strict Offline Mode — بوابة شبكة فاشلة-بأمان (T1.7، جزئي)
- `ara_cloud::NetworkPolicy` (`Online` | `StrictOffline`) يُفحَص **قبل** بناء أي طلب — `list_models` و`CloudModel::generate_chat` يرفضان فورًا تحت `StrictOffline` دون محاولة فتح socket، لا بعد فشل اتصال.
- **مُختبر بدليل شبكي فعلي لا افتراض منطقي فقط**: اختبار يفتح `TcpListener` محلي يقوم بدور "البروكسي/سجل الاتصالات" الذي يطلبه معيار القبول في `ROADMAP_TASKS.md` T1.7، ويثبت صفر محاولة اتصال تحت `StrictOffline` (ثم يثبت العكس تحت `Online` بلا خادم TLS حقيقي خلفه — فحص سلامة الاختبار نفسه، لإثبات أن الصفر معناه حظر فعلي لا خلل صامت في مكان آخر).
- **تحديث (2026-11-25):** `Settings.strict_offline: bool` (افتراضي `false`) + `AraCore::{set_strict_offline, strict_offline, network_policy}` في `ara-ffi::core.rs` — `cloud_models` و`use_cloud_model` يقرآن الإعداد الفعلي الآن بدل `Online` الثابت سابقًا؛ الـ`TODO(T1.7)` القديم في `core.rs` أُغلِق على مستوى Rust. 3 اختبارات: الإعداد يبقى محفوظًا بعد إعادة فتح `AraCore` (restart)، التفعيل يرفض بنص خطأ `NetworkPolicy` قبل أي محاولة شبكة (نفس شهادة عدم-المحاولة لا فحص بعد الفشل)، والتعطيل (الافتراضي) يسمح بمحاولة فعلية.
- **الباقي (غير مكتمل):** هذا وصل Rust↔FFI فقط — **لا مفتاح/شاشة في واجهة Kotlin بعد** يستدعي `set_strict_offline` (لم يُبنَ تطبيق Android في هذه الجلسة لفحصه؛ الإعداد قابل للاستدعاء عبر UniFFI نظريًا لكن غير مُختبَر من الجانب الأندرويدي). لا سجل Privacy Center (ما نُفِّذ ولا نُقَاس ولا نُرسَل) يعرض هذا للمستخدم بعد. تنزيل النماذج (ara-model-manager) غير متأثر عمدًا: التنزيل فعل صريح من المستخدم بالفعل، ليس اتصالًا خلفيًا.

### ADR-016: واجهتا المهام والأمان + WorkManager (T0.3، غير مُختبر على جهاز)
- النواة (`ara-missions`, `ara-sentinel`) وربط FFI (`create_mission`, `missions`, `mission`, `mission_audit`, `set_mission_status`, `resumable_missions`, `run_mission_step`, `decide_mission_approval`, `security_check`) كانوا موجودين ومُختبرين من قبل بدون واجهة. أُضيفت الواجهة فقط؛ منطق الأمان/الميزانية/الموافقات نفسه لم يتغيّر.
- `MissionWorker` (CoroutineWorker): خطوة واحدة محدودة في كل تشغيل (استدعاء موديل واحد محدود، لا حلقة مستمرة في الخلفية)، ثم يعيد جدولة نفسه بـ`WorkManager.enqueueUniqueWork` (REPLACE) لو المهمة لسه `running`، أو يتوقف بصمت لو توقفت/انتهت/محتاجة موافقة (مع إشعار في الحالتين الأخيرتين). عند إغلاق التطبيق أو إعادة تشغيل الهاتف: `MainActivity` يستدعي `resumable_missions` ويعيد جدولة كل مهمة لسه شغالة.
- شاشة الموافقات تستخدم نفس مسار الشات حرفيًا: `decide_mission_approval` → `ToolCall` JSON → `confirm_action` → `Dispatch` → `HostActions.run` لو `run_on_host`. لا مسار تنفيذ مختلف أو أقل تحققًا للمهام.
- `SecurityScreen` يجمع `HostSecurityFacts` من Android APIs العلنية فقط (لا shell، لا استغلال): `ApplicationInfo.FLAG_DEBUGGABLE`، `Settings.Global` لـADB/خيارات المطورين، `KeyguardManager.isDeviceSecure`، `Build.VERSION.SECURITY_PATCH`، `getInstallSourceInfo`، تخمين محاكي من `Build.FINGERPRINT/MODEL/HARDWARE`، ووجود مسارات `su` شائعة. كل حقل اختياري ويُترك غائبًا (لا يُخمَّن) لو فشلت القراءة — يطابق فلسفة `ara_sentinel::HostSecurityFacts` (`#[serde(default)]`).
- **مُختبر:** `./gradlew :app:assembleDebug` و`:app:testDebugUnitTest` (ترجمة Kotlin الفعلية مقابل bindings UniFFI المولَّدة، دمج الموارد والمانيفست). **غير مُختبر:** أي سلوك فعلي على جهاز (استمرار WorkManager بعد إغلاق التطبيق فعليًا، ظهور الإشعار، صحة حقائق الأمان على هاتف حقيقي) — يحتاج T0.2.
- قرار واجهة: 7 تبويبات أسفل الشاشة (أضيف Missions وSecurity) بدل تداخلهم تحت الإعدادات، التزامًا بالنص الحرفي للخطة. ملاحظة صادقة: هذا مزدحم على شاشة هاتف ولم يُختبر بصريًا على جهاز — قد يحتاج مراجعة بعد T0.2.

### ADR-012: API Hub ودرع الخصوصية
- `CloudModel` ينفّذ `LoadedModel` ⇒ نفس المسار للمحلي والسحابي، وواجهة المحادثة تعرض «☁ سحابي» بوضوح.
- https فقط، بلا بيانات اعتماد في الرابط. أخطاء HTTP تُترجم دون أي جزء من المفتاح، و`Debug` لا يطبع المفتاح.
- الموافقة لا تُمنح إلا عبر `set_cloud_consent` (أي `consent` داخل JSON يُتجاهل).
- الدرع مطابقة أنماط (best-effort) ومذكور ذلك للمستخدم في شاشة الموافقة.

### ADR-017: نظام المهارات القابلة للتوسعة (Skills Ecosystem) — دروس من Instinct وClawHub (تصميم لـ T2.2، لم يُنفَّذ)

**الدافع:** طلب صاحب المشروع (2026-11-25) تطوير تصميم مهارات قابلة للتوسعة داخل ARA نفسها (بمنطق شبيه بمهارات Claude Code) بعد بحث منافسين جديد غطّى (أ) **Instinct** (Spear Street Technology) — وكيل سحابي ذو صلاحيات واسعة عبر الإيميل/التقويم/الرسائل/الشاشة/الصوت أثار مخاوف أمنية وخصوصية فعلية وموثَّقة في بيتا خاصة (أغسطس–أكتوبر 2026)، و(ب) حملات تسميم موثَّقة لسوق المهارات **ClawHub** التابع لوكيل OpenClaw (مئات إلى أكثر من ألف مهارة خبيثة عبر عدة عمليات فحص مستقلة). التفاصيل الكاملة والمصادر: `research_notes/تحليل Instinct ومنصات المهارات/` و `reports/تحليل Instinct ودروس أمنية لنظام المهارات.md`. هذا ADR هو القرار المعماري الناتج، لا تغييرًا في ترتيب الأولوية.

**القرار الأهم: المهارة بيانات، لا برنامج.** `SkillManifest` الحالي (`core/crates/ara-tools/src/skills.rs`) يبقى، في جوهره، نفس الشكل للمهارات الخارجية: `id`/`version`/`name`/`description`/`instructions`/`tools` — بلا حقل كود أو سكريبت أو أي سطح تنفيذ جديد. هذا يُسقط تلقائيًا الفئة الأخطر من هجمات ClawHub (سكريبتات مجمّعة تعمل بصلاحيات المستخدم الكاملة وتقرأ متغيرات البيئة — السبب المباشر لسرقة بيانات الاعتماد في تحليل Lakera): لا يوجد مُفسِّر سكريبت مكشوف للمهارات من الأساس، فلا حاجة لصندوق (sandbox) نهرب منه لأنه لا يوجد سطح تنفيذي بالمعنى الذي استُغِلّ هناك — فقط نص يُضاف للسياق وقائمة أدوات *موجودة فعلًا* يُطلَب تفعيلها.

- `instructions` تبقى غير موثوقة دائمًا — امتداد مباشر لقاعدة T1.9 («نتائج الأدوات بيانات لا تعليمات») لمحتوى المهارة نفسها: تُدرَج في system prompt كمحتوى وصفي، لا كقواعد توجيه تغيّر منطق النواة؛ لا تُسقط صلاحية أو تأكيد أي أداة. هذا موجود فعلًا كتعليق في الكود (`skills.rs:3-5`: "their instructions will be treated as untrusted and can never widen the permissions of a tool") — هذا ADR يحوّله من تعليق إلى قرار معماري مكتوب ومُختبَر.
- `tools: Vec<String>` تبقى قائمة من أدوات ARA **الموجودة فعلًا فقط** (الأدوات المُسجَّلة في `ToolRegistry`) — مهارة خارجية لا تقدر تُعرِّف أداة جديدة أو تطلب shell/تنفيذ كود/وصول خام للملفات. `validate_skill` يرفض أي اسم أداة غير مسجَّل (مُختبر: `unknown_tool_in_skill_is_rejected`). أداة جديدة بالكامل تبقى قرار كود من فريق ARA، لا حمولة مهارة — هذا يطابق النتيجة الأكاديمية في بحث SkillGuard (2026) التي تدعو لنموذج صلاحيات مُجزَّأ بدل منطق "تعليمات = أوامر تشغيل".
- **التفعيل لا يمنح الصلاحية.** تثبيت/تفعيل مهارة يُضيفها لقائمة المهارات المتاحة للموجّه (router) فقط؛ كل أداة تطلبها تمر أول استخدام بنفس بوابة الصلاحية + التأكيد + حد المعدل الموجودة فعلًا (ADR-006)، بما فيها أي أثر External. مهارة لا تقدر تمنح نفسها "مسموح دائمًا" بالنيابة عن المستخدم.
- **طبقات ثقة (trust tiers) بدل سوق مفتوح واحد:**
  1. **مدمجة (built-in):** كما الآن، داخل الـ APK، تُراجَع مع كل تعديل كود.
  2. **موثّقة من ARA (ara-verified):** مُراجَعة (حتى يدويًا بحجم المشروع الحالي) ومُوقَّعة بمفتاح ARA قبل ظهورها في أي قائمة داخل التطبيق — نفس فلسفة كتالوج النماذج (ADR-004): عدد صغير مُتحقَّق، لا سوق ذاتي الخدمة مفتوح لآلاف المهارات. هذا بالضبط الفرق الذي وجده البحث بين فشل ClawHub (فحص آلي عند النشر فقط، تجاوزه 5 مهارات خبيثة حسب Unit 42) ونجاح نسبي Google AI Edge Gallery (صلاحيات مُعلَنة لكل قدرة، يفرضها المُشغِّل لا كود المهارة).
  3. **مستورَدة من المستخدم (دَوري/مجتمعي):** استيراد ملف/رابط JSON يدويًا، مع تحذير صريح غير قابل للتجاوز بنقرة واحدة يذكر: غير مراجَعة من ARA + قائمة الأدوات المطلوبة بلغة مباشرة، قبل أي تفعيل.
  4. لا طبقة تمنح تنفيذ كود مطلقًا — الفرق بين الطبقات هو مستوى المراجعة والتوقيع، لا مستوى الصلاحيات التقنية (تبقى نفس بوابة ADR-006 في كل الحالات).
- **التحديث لا يرث الثقة.** أي تغيير في `instructions` أو `tools` لنسخة جديدة من مهارة (موثّقة أو مستوردة) يُعرَض للمستخدم كفرق واضح (الأدوات الجديدة المطلوبة إن وُجدت) قبل التفعيل، والتوقيع يُعاد فحصه في كل تفعيل/تحديث لا مرة واحدة فقط. يقفل هذا تحديدًا الثغرة التي وثّقها بحث ClawHub: مهارة اعتُمدت بعد المراجعة الأولى ثم عُدِّلت لإضافة استغلال دون مراجعة ثانية.
- **الإلغاء (revocation).** قائمة حظر صغيرة موقّعة تُوزَّع مع تحديثات التطبيق وتُحدَّث عند الاتصال، بلا إلزام شبكي لتشغيل مهارة (يطابق مبدأ Strict Offline/ADR-015): آخر نسخة معروفة محليًا تُستخدَم إن كان الجهاز بلا إنترنت — تنازل صريح موثَّق، لا سلوك صامت. تعطيل/حذف مهارة من المستخدم = إزالة فورية لربطها بأي أداة، لا عند إعادة تشغيل التطبيق.
- **كل فعل مهارة قابل للتتبع** عبر سجل Privacy Center المخطط في T1.7 (أي مهارة فعلت أي شيء ومتى) — التحقق سجل قابل للفحص محليًا، لا وعدًا تسويقيًا.
- **الفرق المتعمَّد عن Instinct:** مشكلة Instinct في البحث ليست سوق مهارات مُستغَل — هي غياب أي نموذج صلاحيات مُجزَّأ من الأساس: موافقة واحدة عريضة على الوصول لإيميل/تقويم/رسائل/شاشة/صوت، بلا تأكيد قبل كل فعل خارجي (حادثة Katie Stanton المُوثَّقة: إيميل أُرسِل بلا أي تأكيد مسبق)، وبلا حذف موثوق بعد قطع الاتصال (حادثتا Peter Yang وClaire Vo). هذا يطابق تمامًا ما يمنعه `dispatch()` الحالي في ARA (تأكيد إلزامي لأي أثر External حتى تحت صلاحية "دائمًا"، مُختبر فعليًا في T1.9 بسبع هجمات حقن تعليمات، صفر تنفيذ صامت) — أي أن أهم ضمانة لدى ARA في مواجهة هذا النوع من الفشل **مُختبرة فعليًا من قبل** هذا القرار، لا جديدة بسببه.
- **غير محسوم عمدًا (قرارات تفصيلية لاحقة، لا الآن):** شكل التوقيع الفعلي (مرشَّح Ed25519 بمكتبة Rust خالصة، بلا تبعية native جديدة، بنفس منطق تفضيل T1.8 لتشفير ظرفي على SQLCipher)، الحقول الإضافية للمانيفست الموزَّع (`publisher`/`signature`/`min_ara_version` تُضاف لاحقًا فوق `SkillManifest` الحالي، لا تستبدله)، وتصميم شاشة استيراد/تصفح المهارات في `SkillsScreen.kt` الموجودة.
- **لا تغيير في ترتيب الأولوية.** يبقى T2.2 بعد P0/P1 كما في `docs/ROADMAP_TASKS.md`، والقرار الصريح لصاحب المشروع «لا متجر مهارات الآن» (§1) لا يتغيّر بهذا ADR — هذا تصميم جاهز للتنفيذ وقت دوره، لا جدولة جديدة. التفصيل الكامل لتقسيم T2.2 إلى مهام فرعية بمعايير قبول: `docs/ROADMAP_TASKS.md` §P2.
- **تحديث (نفس اليوم، 2026-11-25):** T2.2a وT2.2b مُنفَّذتان جزئيًا بكود حقيقي ومُختبَر — `SkillManifest` فيها الآن `publisher`/`trust_tier`/`signature`/`min_ara_version`، ودوال `signable_bytes`/`verify_signature`/`validate_signed_skill` في `core/crates/ara-tools/src/skills.rs`. التفاصيل الكاملة (الكريبتو المستخدمة، الاختبارات، ما تبقّى) في ADR-018 التالي — هذا تنفيذ جزئي للتصميم أعلاه، لا تصميم جديد.
- **تحديث ثانٍ (نفس اليوم):** T2.2c (استيراد يدوي) وT2.2d (إلغاء) مُنفَّذتان جزئيًا أيضًا — `AraCore::import_skill`/`delete_imported_skill` (`ara-ffi::core.rs`) يفرضان `trust_tier = Imported` على أي ملف مستورَد بلا شرط (لا يقدر يدّعي ثقة أعلى)، ويرفضان أداة غير موجودة أو تصادم id مع مهارة مدمجة. `skills::is_blocked` + `AraCore::set_skill_blocklist` يفلتران `all_skills()` فورًا — مهارة تُحظَر بعد استيرادها تختفي من القائمة في الاستدعاء التالي مباشرة، لا عند إعادة تشغيل. **كل هذا في Rust/FFI فقط** — لا شاشة Kotlin تعرض تحذير الاستيراد أو زر الحذف بعد؛ التفاصيل والاختبارات في `docs/ROADMAP_TASKS.md` T2.2c/T2.2d.

### ADR-018: `ara-crypto` — تشفير ظرفي (T1.8) وتوقيع مهارات (T2.2b) بمكتبة واحدة بلا تبعية native جديدة

**القرار المُنفَّذ (2026-11-25):** كريت جديد `core/crates/ara-crypto` يقدّم كل التشفير/التوقيع اللازم لـT1.8 وT2.2b بمكتبة واحدة هي **`ring 0.17.14`** — ليست تبعية جديدة فعليًا: `ring` مُجمَّعة بالفعل في شجرة الاعتماديات لأن `ureq` (مُستخدَمة في `ara-cloud` و`ara-model-manager` لتنزيل النماذج عبر HTTPS) تفعّل `rustls` التي تعتمد على `ring` كخلفية تشفير. استخدامها مباشرة هنا لا يضيف مكتبة C/asm جديدة للتقطير عبر NDK، فقط يستخدم ما يُجمَّع للأندرويد الآن.

- **تشفير ظرفي (`seal`/`open`):** AES-256-GCM، `nonce` عشوائي 12 بايت جديد لكل استدعاء (لا إعادة استخدام)، الصيغة `[إصدار(1 بايت) | nonce(12) | نص مشفَّر+tag]` — بايت الإصدار يجعل أي تغيير مستقبلي في الصيغة يفشل بوضوح على بيانات قديمة بدل تخريبها بصمت. `generate_key()` يولّد مفتاح بيانات (DEK) عشوائيًا فقط — **لا تغليف Keystore هنا**؛ تغليف الـDEK بمفتاح Keystore (KEK) مسؤولية Kotlin، ولا يزال غير موصول (نفس نمط `TODO(T1.7)` في ADR-015 بالضبط).
- **تطبيق فعلي، لا بناء تحتي نظري فقط:** `ConversationStore::open_with_key` (`ara-ffi::conversations`) يُشفِّر كل ملف محادثة JSON على القرص. `open` (بلا مفتاح) يبقي السلوك القديم بلا أي تغيير — خيار الانضمام (opt-in) لا تغيير افتراضي. مُختبَر فعليًا بما يطابق معيار قبول T1.8 حرفيًا: الملف الخام على القرص لا يحتوي النص الصريح (`fs::read` + فحص سلاسل)، المفتاح الخطأ يفشل في القراءة (اختبار استعادة)، وملف غير مشفَّر لا يُقرَأ خطأً كمشفَّر (والعكس) — متجران (مشفَّر/غير مشفَّر) على نفس المجلد لا يختلطان بصمت.
- **توقيع/تحقق (`generate_keypair`/`sign`/`verify_signature`):** Ed25519 عبر `ring::signature`. التوقيع (offline tooling فقط — لا يحدث أبدًا داخل التطبيق وقت التشغيل) والتحقق (الوحيد المُستخدَم فعليًا في التطبيق، ضد مفتاح ARA العام المُضمَّن). مُستخدَم في `ara-tools::skills::{verify_signature, validate_signed_skill}` (ADR-017/T2.2b) — تفاصيل الاختبارات في `docs/ROADMAP_TASKS.md` T2.2b.
- **ملاحظة أمنية اكتُشفت أثناء الاختبار، موثَّقة في كود `ara-crypto` (`malformed_key_or_signature_never_panics`):** مفتاح عام صفري بالكامل مع توقيع صفري بالكامل "يتحقق" تحت معادلة Ed25519 القياسية المُكوفَكترة — خاصية رياضية معروفة للمخطط (نقطة منخفضة الرتبة/الهوية)، ليست ثغرة في `ring` أو في هذا الكريت. **لا تأثير عملي على ARA** لأن `verify_signature` لا يُستدعى إلا بمفتاح عام *ثابت ومُضمَّن في ARA نفسها*؛ لا مسار في التصميم يسمح لطرف خارجي باقتراح "مفتاح موثوق" بديل — لو استطاع مهاجم فعل ذلك فهو فاز من طريق آخر أصلًا.
- **الباقي (صادقة، لا تخمين):** `index.db` (SQLite/FTS5) غير مُشفَّر بعد — أصعب تقنيًا من ملفات المحادثات لأن الفهرسة النصية تحتاج نصًا مُطبَّعًا قابلًا للمطابقة، فالتشفير هنا سيكون على مستوى الحقل (مثلًا نص المستند الخام نفسه، لا رموز الفهرسة) لا الملف كاملًا — قرار تفصيلي لم يُتَّخذ بعد. لا وصل Keystore فعلي من Kotlin (`ara-ffi` لا يستدعي `open_with_key` خارج اختباراته الخاصة). لا مفتاح عام حقيقي لـARA مُضمَّن في التطبيق بعد، ولا مهارة `ara-verified` واحدة موجودة لتوقيعها، ولا أداة توقيع (CLI) فعلية.

### ADR-019: سجل النشاط المحلي (Privacy Center، T1.7/T2.2e) — بيانات وصفية فقط

**القرار:** `ara-ffi::activity_log` — ملف JSON واحد (`activity.json`) يسجّل *فقط*: الوقت، الأداة، المهارات الموجِّهة لها، معرّف المحادثة/المهمة (إن وُجد)، والنتيجة (`done`/`needs_confirmation`/`run_on_host`/`run_service`/`denied` — مُستخرَجة من `ara_tools::Dispatch` الموجود، لا نوع جديد). **لا وسيطات الاستدعاء ولا مخرجاته تُسجَّل أبدًا** — هذا يجيب "هل سمح لهذا الفعل أم رُفض"، لا "ماذا قلت لـARA"؛ محتوى الرسائل يبقى فقط في محادثته (ومُشفَّرًا لو T1.8 مفعَّلة).

- **سقف نمو صارم:** `MAX_ENTRIES = 500`، تُحذَف الأقدم أولًا — نفس منطق `MAX_LEARNED_ALIASES` (ADR-013): لا يمكن أن يكبر هذا الملف بلا حدود بطول الاستخدام.
- **موصول فعليًا، لا مُجرَّد تصميم:** `AraCore::send_message` وخطوة المهمة (`run_mission_step`) يسجّلان كل `ToolEvent` من `TurnResult`؛ `confirm_action` يسجّل النتيجة النهائية بعد الموافقة (بما فيها تحويل `RunService` الناجح إلى `Done` قبل التسجيل). كل كتابة سجل غير قاتلة (`let _ = ...append(...)`) — فشل كتابة السجل لا يجب أن يُفقِد فعلًا حقيقيًا حدث فعلًا (المحادثة تُحفَظ أولًا دائمًا).
- **مُختبَر بفحص بايتات الملف الفعلية**، لا افتراض من الـschema: `log_never_contains_the_call_arguments_or_output` يضع كلمة سرية في مخرجات أداة وهمية ويثبت غيابها الحرفي من الملف المكتوب على القرص.
- **`AraCore::activity_log(limit)`** — دالة FFI تعرض السجل الأحدث أولًا؛ هذا أول شيء فعلي وراء اسم "Privacy Center" في الوثائق، لا مجرد وعد.
- **الباقي:** لا شاشة Kotlin تعرضه بعد. لا فحص نسخ احتياطي/سجلات مستقل عن `allowBackup=false` الموجود (الجزء الآخر من T1.7). لا تمييز بين أنواع الطلبات (محلي/سحابي) في السجل حاليًا — كل الإدخالات حتى الآن من المسار المحلي؛ تمييز استدعاءات API Hub السحابية سيحتاج تعديلًا منفصلًا صغيرًا عند الحاجة.

### ADR-020: `ara-smarthome` — تحكم بيت ذكي عبر Home Assistant، لا بروتوكول أجهزة مباشر

**القرار (2026-11-25، استجابة لطلب "البيت الذكي" في جلسة توسعة — تفاصيل الجدوى الكاملة في `docs/EXPANSION_BLUEPRINT.md` الفئة M):** كريت جديد `core/crates/ara-smarthome` يتكلم مع Home Assistant (REST API محلي، توكن طويل الأمد يضيفه المستخدم) بدل محاولة دعم أي بروتوكول أجهزة ذكية مباشرة (Zigbee/Z-Wave/Matter/واجهات كل شركة على حدة) — نفس فلسفة ADR-004 (كتالوج نماذج من ناشرين رسميين بس، لا نبني كل شيء بأنفسنا) وAPI Hub (مفتاح المستخدم الخاص، لا مزوّد نديره نحن).

- **شبكة محلية لا إنترنت عام:** خلافًا لـ`ara-cloud` (https فقط، بلا استثناء)، أغلب تنصيبات Home Assistant المنزلية تعمل على `http://` عادي داخل الشبكة المحلية بدون شهادة TLS عامة. `validate_base_url` هنا يقبل `http://` أو `https://` عمدًا — قرار موثَّق في كود الكريت نفسه، لا سهو — مع رفض أي مخطط URL آخر وأي بيانات اعتماد مُضمَّنة في الرابط.
- **مُنفَّذ ومُختبر فعليًا (لا تصميم فقط):** `HomeAssistant::{ping, states, call_service}` + خادم وهمي محلي (`TcpListener`، نفس نمط اختبار `ara-cloud`) يثبت: تحليل حالات الكيانات (`entity_id`/`state`/`friendly_name`)، إرسال رمز Bearer في الترويسة، مسار وجسم POST الصحيحين لاستدعاء خدمة، ورفض توكن خاطئ برسالة واضحة لا تسرّب التوكن نفسه. 5 اختبارات، كلها ناجحة.
- **الباقي (صريح، لا ادعاء):** هذا الكريت **غير مسجَّل في `ToolRegistry`** — الموجّه لا يقدر يستدعيه، ولا شيء في `ara-ffi` يعرضه لـKotlin. التحكم في جهاز حقيقي (تشغيل نور، فتح قفل) أثر External حقيقي، ولازم يمر بنفس بوابة التأكيد الإلزامي (ADR-006) قبل ما يبقى قابلًا للوصول من أي محادثة — ده عمل منفصل متعمَّد، مش عجلة مش مكتملة. لا تخزين Keystore للتوكن من Kotlin بعد (نفس نمط `TODO` في ADR-015/018: الجزء الصعب أمنيًا مبني ومُختبر، الربط بالتخزين الآمن الحقيقي يحتاج جهاز Android فعليًا لبنائه عليه).

**تحديث لاحق (نفس اليوم):** تم استخدام `smarthomeConnect`/`smarthomeBaseUrl` الفعليين الآن من Kotlin (`SmartHomeSection.kt`) — التوكن يُخزَّن عبر `KeyVault` (نفس نمط مفاتيح API Hub)، ولا يصل أبدًا لملف `settings.json`. لسه غير موصول بـ`ToolRegistry`/الموجّه كما هو موثَّق أعلاه.

### ADR-021: `ara-backup` — تصدير/استيراد مشفّر بعبارة مرور، لا سحابة ولا سيرفر

**القرار (2026-11-26، استجابة لطلب "قوّي المشروع" — فجوة "Backup and recovery" كانت `MISSING` في `docs/MASTER_CAPABILITY_REGISTRY.md`):** كريت جديد `core/crates/ara-backup` يحزم مجلد بيانات آرا (المحادثات، index.db، الإعدادات، الصلاحيات) في أرشيف واحد مشفَّر بمفتاح مُشتَق من عبارة مرور يختارها المستخدم (PBKDF2-HMAC-SHA256، 210,000 تكرار — تنازل صريح وموثَّق عن توصية OWASP الحالية 600 ألف، بسبب تكلفة المعالجة على هاتف بلا تسريع عتادي لـPBKDF2) ثم `ara_crypto::seal` (AES-256-GCM، نفس الأساس المُختبر من ADR-018) — لا اعتماد جديد على مكتبة تشفير.

- **الصيغة:** تسلسل مسطّح من المدخلات (`[طول المسار][المسار][طول المحتوى][المحتوى]`) يُشفَّر ككتلة واحدة؛ رأس الأرشيف (`"ARAB"` + رقم إصدار + ملح عشوائي 16 بايت) غير مشفَّر عمدًا (الملح ليس سرًا، نفس دور nonce داخل `seal`).
- **`models/` مستبعد دائمًا من المُستدعي** (لا الكريت يفرضه، المتصل يمرّره) — ملفات GGUF بالجيجابايتات يعاد تنزيلها من ناشرها الرسمي أصلًا (ADR-004)، نسخها احتياطيًا بلا فائدة حقيقية.
- **مُختبر فعليًا بسيناريوهات هجوم حقيقية، لا سعادة الطريق فقط:** 6 اختبارات — جولة ذهاب وعودة كاملة تحافظ على البنية، عبارة مرور خاطئة تُرفَض برسالة واضحة، عبارة مرور فارغة تُرفَض قبل أي عمل، أرشيف مُلاعَب (تغيير بايت واحد) يُرفَض بفحص GCM tag، **أرشيف مصنوع يدويًا بمسار `"../../etc/evil"` يُرفَض ولا يُكتَب خارج مجلد الاستعادة** (الاختبار يتجاوز `export` نفسها عمدًا ليثبت أن `import` نفسه يرفض، لا الثقة في أن `export` لن تنتج مسارًا كهذا أبدًا)، واستبعاد `models/` يُثبَت بعدّ ملفات حقيقي لا افتراض.
- **نموذج التهديد، بصراحة:** هذا يحمي ملف الأرشيف نفسه في مكان مثل Downloads أو بطاقة SD أو مجلد مزامنة سحابي — لا يحمي من جهاز مخترَق وقت تشغيل آرا نفسه، ونسيان عبارة المرور يجعل الأرشيف غير قابل للاسترجاع نهائيًا (لا باب خلفي، لا آلية استرداد، بالتصميم — نفس وضع مفتاح Keystore المفقود).
- **الباقي (صريح، لا ادعاء):** لا واجهة Kotlin تستدعي هذا بعد (لا منتقي ملف SAF لاختيار مكان حفظ/فتح الأرشيف، لا شاشة إدخال عبارة مرور، لا شريط تقدّم لمجلد بيانات كبير) — نفس نمط `ara-crypto`/`ara-smarthome` قبل ربط واجهتهما.
