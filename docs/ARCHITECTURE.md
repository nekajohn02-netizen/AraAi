# ARA — البنية المعمارية

## الطبقات
```
Kotlin / Compose ─ ChatScreen · ModelsScreen · SkillsScreen · SettingsScreen
   │  CoreBridge (Dispatchers.IO)      HostActions (Intents — قائمة مسموحة ثابتة)
   │  UniFFI: AraCore + TextListener/ProgressListener/CancelHandle
   ▼
ara-ffi ── AraCore (حالة التطبيق) + conversations (JSON محلي)
   ├─ ara-coordinator   توجيه المهارات → RAG → سياق محدود → توليد → أدوات → إجابة
   ├─ ara-search        SQLite FTS5 + تطبيع عربي + تقاطع لهجات/لغات + ذاكرة المستخدم (index.db)
   ├─ ara-cloud         API Hub (OpenAI-compatible SSE) + Privacy Shield
   │     ├─ ara-inference (+llama.cpp عبر llama-cpp-2، CPU)
   │     └─ ara-tools     manifests · schema · policy · parse · builtin · skills
   ├─ ara-model-manager  تنزيل مستأنف · SHA-256 · حد مساحة · قفل · حذف آمن
   ├─ ara-model-selector استبعاد + ترتيب بطبقات + معايرة بالقياس
   ├─ ara-model-registry كتالوج JSON (core/catalog/models.json)
   ├─ ara-device-profiler /proc/meminfo · statvfs · /proc/self/status
   └─ ara-core-api       أخطاء · أحداث · إلغاء
ara-cli: أداة مطور تشغّل نفس النواة (profile/models/download/bench/chat/agent)
```
منطق الأعمال كله في Rust. Kotlin يجمع حقائق المنصة وينفذ Intents التي وافقت عليها النواة.

## قرارات معمارية

### ADR-001: UniFFI بدل JNI يدوي
مُختبر: ترجمة الربط المولّد داخل التطبيق، 5 اختبارات JVM عبر JNA. اكتُشف تعارض حقل `message` مع `Throwable.message` ⇒ حقول الأخطاء اسمها `detail`.

### ADR-002: JSON عبر الجسر للهياكل المركبة
الكائن `AraCore` مطبوع النوع، والهياكل الكبيرة (قائمة النماذج، نتيجة الدور) JSON مملوكة لـ serde. يُعاد التقييم عند استقرار الـ schemas.

### ADR-003: اختيار النموذج
- الاستبعاد: الرام المتاحة × 0.85 − 512MB؛ التقدير = حجم الملف + KV (من معمارية النموذج: طبقات × رؤوس KV × بُعد الرأس × 2 × 2 بايت) × السياق + 256MB.
- السرعة المقدّرة = عرض النطاق ÷ حجم الملف (التوليد على CPU محدود بالذاكرة). الافتراضي 6 GB/s ثم يُعايَر بوسيط القياسات الفعلية.
- الترتيب بطبقات قابلة للشرح؛ داخل الطبقة: جودة (log المعاملات، خصم بسيط لـ 4-bit) وسرعة على مقياس لوغاريتمي.

### ADR-004: كتالوج النماذج
فقط ناشرون رسميون وتراخيص Apache-2.0/MIT وملف واحد. مستبعد عمدًا: Qwen2.5-3B (رخصة بحثية)، Gemma (شروط خاصة/مقيد)، Phi-4-mini (رفع طرف ثالث)، 7B (ملفات مقسمة). يُولّد بـ `scripts/gen_catalog.py` من بيانات Hugging Face API (الحجم وsha256 من LFS).

### ADR-005: llama.cpp عبر `llama-cpp-2` 0.1.161
مُثبّت الإصدار. على Android: libc++ ثابت ⇒ `.so` واحد يعتمد فقط على libc/libm/libdl (~10MB لكل معمارية). سياق جديد لكل طلب (تبسيط للـ lifetimes)؛ إعادة استخدام KV مؤجلة.

### ADR-006: المهارات والأدوات
- الأداة تعلن: schema صارم (رفض المفاتيح المجهولة، حدود الطول بالحروف)، صلاحيات، نوع الأثر (None/Reversible/External)، Core/Host، مهلة، حد مخرجات، حد معدل.
- `dispatch` نقطة الدخول الوحيدة: tool مجهول ⇒ رفض؛ schema ⇒ precheck دلالي (https فقط، أرقام هواتف، تواريخ) ⇒ صلاحية المستخدم ⇒ تأكيد ⇒ حد المعدل ⇒ تنفيذ.
- **أي أثر External يطلب تأكيدًا دائمًا** حتى لو كانت الصلاحية "مسموح".
- لا أداة Shell أو تنفيذ كود.
- **الموجّه (router)**: كلمات مفتاحية عربي/مصري/إنجليزي تختار المهارات ذات الصلة فقط ⇒ الـ prompt نزل من ~1800 إلى ~550 token.
- صيغة الأدوات مطابقة حرفيًا لقالب Qwen الرسمي (التجربة أظهرت أن صياغة مختلفة جعلت 1.5B يرفض المهام).

### ADR-007: واتساب وتيليجرام والسوشيال
- الآن: Intents رسمية تفتح التطبيق بالمحتوى جاهزًا، والمستخدم يضغط إرسال. مجاني، لا مفاتيح، لا مخالفة لشروط الخدمة، لا إرسال خفي.
- لا نستخدم Accessibility لأتمتة واتساب (مخالف للشروط وخطر أمني).
- لاحقًا (G9): Telegram Bot API للتحكم عن بُعد (خادم + توكن، تحقق الهوية على الخادم)، WhatsApp Business Cloud API للحسابات التجارية فقط.

### ADR-008: الرام والمساحة
- نموذج واحد مقيم؛ تفريغه عند `onTrimMemory(BACKGROUND)` أو تبديل النموذج.
- حجم السياق قابل للضبط (2K/4K/8K) ويؤثر مباشرة على KV cache.
- حد مساحة للنماذج يختاره المستخدم + 1GB مساحة حرة دائمًا.
- الأوزان mmap (llama.cpp) فلا تُنسخ في الذاكرة.

### ADR-009: إعادة استخدام KV cache
السياق يعيش مع النموذج (`self_cell` بدل `unsafe`). في كل طلب: أطول بادئة مشتركة من الـ tokens تبقى، ويُحذف الباقي بـ `clear_kv_cache_seq`، ويُقيَّم الذيل الجديد فقط. إن فشل الحذف الجزئي (بعض المعماريات) ⇒ مسح كامل. أي خطأ ⇒ مسح الكاش حتى لا يبقى غير متسق.

### ADR-010: البحث والذاكرة
- SQLite (rusqlite 0.41.1 bundled) في ملف واحد `index.db`: documents/chunks + FTS5 contentless على نص مُطبّع.
- التطبيع العربي نفسه للفهرسة والاستعلام: حذف التشكيل والتطويل، توحيد أ/إ/آ/ٱ→ا، ى→ي، ة→ه، ؤ→و، ئ→ي، أرقام عربية→لاتينية.
- كل كلمة في الاستعلام بين علامتي تنصيص ⇒ لا حقن لصيغة FTS5.
- المقاطع ~800 حرف مع تداخل؛ رقم السطر في الاستشهاد هو السطر الأكثر تطابقًا داخل المقطع.
- RAG حتمي: عند توجيه مهارة «ملفاتي» تبحث النواة أولًا (بنفس فحص الصلاحيات) وتضع المقاطع مع مصادرها قبل السؤال، ولا تُحفظ في المحادثة.
- الذاكرة: لا حفظ تلقائي؛ أداة `remember` تحتاج صلاحية + تأكيد، والمستخدم يضيف/يعطّل/يحذف. الذكريات المفعلة تُضاف للـ system prompt بحد 1200 حرف.
- أنواع الأدوات: Core (حساب نقي) / Host (Intents في Kotlin) / Service (حالة داخل النواة: البحث والذاكرة).

### ADR-011: الأوضاع المتخصصة (Personas)
نص الوضع موثوق (first-party) ولا يوسّع صلاحيات أي أداة. الوضع يضيف مهارات دائمة لكن **لا يفرض البحث في الملفات** (البحث الحتمي يحدث فقط إن سأل المستخدم عن ملفاته؛ التجربة أظهرت أن فرضه أفسد الإجابات). صياغة وضع الأمن إيجابية ومحددة لأن الصياغة المليئة بالمحظورات جعلت النموذج الصغير يرفض مراجعة كود عادي.

### ADR-013: تحسين العربية بلا تدريب (crosswalk + aliases مُتعلّمة من المستخدم)
**القرار:** لا نموذج يُدرَّب/يُضبَط (fine-tune) لتحسين فهم اللهجة. السبب: التدريب يحتاج GPU ومجموعة بيانات ومعايرة مستمرة، والنتيجة لسه لازم تضبط في رام الهاتف — تكلفة وخطر على "صحة الجهاز" بدون ضرورة، بينما مشكلة الاسترجاع (لا التوليد) تُحل برُكّة مرادفات.
- `core/lexicon/ar_crosswalk.json` — جدول ثابت (مصري/فصحى/إنجليزي، مثل «الذكاء الاصطناعي التوليدي» ↔ «Generative AI») يُعدَّل كبيانات بدون إعادة تدريب أو حتى إعادة بناء المنطق. يُحمَّل مرة واحدة (`OnceLock`) بحجم كيلوبايتات قليلة.
- `learned_aliases` في `index.db`: تعلّم من تفاعل المستخدم نفسه — **لا كتابة تلقائية أبدًا** (نفس قاعدة الذاكرة)، فقط عند تأكيد صريح (`confirm_alias`). محدود بسقف صارم `MAX_LEARNED_ALIASES = 2000` صفًا مع إخلاء الأقل استخدامًا/الأقدم ⇒ لا يمكن أن ينمو التخزين أو زمن الاستعلام بلا حدود.
- التوسيع عند البحث فقط (لا يُغيَّر الفهرس): كل كلمة/عبارة في الاستعلام تُقارَن بالعبارة كاملة (مطابقة بحدود كلمة، لا تطابق جزئي داخل كلمة أخرى) ثم تُضاف مرادفاتها OR، بحد أقصى `MAX_QUERY_TERMS = 24` لكل استعلام. تكلفة المعالج: مسح خطي لعشرات المجموعات القصيرة — لا نموذج يُشغَّل، فلا أثر يُذكر على الرام أو البطارية أو الحرارة.
- البحث الدلالي بتضمينات (T1.2) يبقى مخططًا ومنفصلاً: عند تنفيذه سيستخدم نموذج تضمين **جاهز ومُدرَّب مسبقًا** (لن نُدرّب نحن نموذجًا) ويُفعَّل فقط حسب فئة الجهاز (`ara-device-profiler`)، مع سقوط آمن (fallback) للبحث النصي وحده على الأجهزة الضعيفة.
- مُختبر: `core/crates/ara-search/src/lexicon.rs` و `lib.rs` (20 اختبارًا تشمل تقاطع لهجة/لغة، تعلّم عند التأكيد فقط، وثبات السقف `MAX_LEARNED_ALIASES` بعد تجاوزه).
- **إصلاح (2026-11-25، اكتُشف أثناء بناء T1.3):** اختيار "أفضل سطر داخل المقطع" للاستشهاد كان يحسب التداخل بكلمات الاستعلام *الحرفية* فقط، لا الموسَّعة. نتيجته: نتيجة وصلت فقط عبر تقاطع لهجات/لغات (الاستعلام لا يطابق المستند حرفيًا بأي كلمة) كانت تُستشهَد بسطر عشوائي (آخر سطر، بسبب كسر التعادل) بدل السطر الذي طابق فعليًا. الإصلاح: الحساب الآن يستخدم قائمة الكلمات الموسَّعة نفسها. اختبار `crosswalk_driven_hits_cite_the_right_line_not_just_the_right_document` يثبت الانحدار (فشل فعليًا بالمنطق القديم قبل الإصلاح، نجح بعده) — ملاحظة مهمة اكتُشفت بالتجربة: المرادفات بلا "ال" (مثل `مهمه`) لا تطابق نفس الكلمة بأل التعريف (`المهمه`) على مستوى FTS tokenizer (لا تدخل اشتقاق/تجريد)، فبعض أمثلة التقاطع الحقيقية تحتاج صياغة تتجنّب "ال" على الكلمة المستهدَفة — قيد معروف، لا حل كامل له الآن.

### ADR-014: استخراج PDF واستشهاد بالصفحة (T1.1)
- `pdf-extract` (Rust خالص، MIT) يستخرج النص صفحة بصفحة (`extract_text_from_mem_by_pages`) — بلا مكتبة native خارجية، بلا OCR (ملف PDF ممسوح كصورة بلا طبقة نص يُرفض بوضوح، لا يُفهرَس فاضيًا).
- `documents.page_starts` (JSON، عمود اختياري NULL لغير PDF) يخزّن أول سطر لكل صفحة في النص المُستخرَج المُجمَّع؛ `extract::page_for_line` يحوّل أي سطر عام لرقم صفحة بمسح خطي على عدد صفحات الملف (عشرات عادة) — لا فهرس إضافي ولا تكلفة تُذكر.
- الاستشهاد في `search()` يرجّح الصفحة: مستند PDF ⇒ `"name.pdf:page 3"`، مستند نصي ⇒ `"name.txt:42"` (كما كان). التعديل في `ara-coordinator::IndexServices` فقط؛ لا تغيير على عقد الأداة.
- مُختبر بملفات PDF حقيقية مبنية بـ`lopdf` (ليست بايتات مُلفَّقة): استخراج نص 3 صفحات، تتبّع حدود الصفحات، رفض PDF بلا نص، واستشهاد صحيح بالصفحة عبر `SearchIndex` كاملة (5 اختبارات جديدة في `extract.rs` + `lib.rs`).
- لم يُقَس بعد: Recall@K/MRR على مجموعة 20 سؤالًا (معيار القبول الكامل لـ T1.1 في `ROADMAP_TASKS.md`) — هذا يحتاج مجموعة تقييم PDF حقيقية لم تُجهَّز بعد.

### ADR-015: Strict Offline Mode — بوابة شبكة فاشلة-بأمان (T1.7، جزئي)
- `ara_cloud::NetworkPolicy` (`Online` | `StrictOffline`) يُفحَص **قبل** بناء أي طلب — `list_models` و`CloudModel::generate_chat` يرفضان فورًا تحت `StrictOffline` دون محاولة فتح socket، لا بعد فشل اتصال.
- **مُختبر بدليل شبكي فعلي لا افتراض منطقي فقط**: اختبار يفتح `TcpListener` محلي يقوم بدور "البروكسي/سجل الاتصالات" الذي يطلبه معيار القبول في `ROADMAP_TASKS.md` T1.7، ويثبت صفر محاولة اتصال تحت `StrictOffline` (ثم يثبت العكس تحت `Online` بلا خادم TLS حقيقي خلفه — فحص سلامة الاختبار نفسه، لإثبات أن الصفر معناه حظر فعلي لا خلل صامت في مكان آخر).
- **الباقي (غير مكتمل):** `NetworkPolicy` موجود في `ara-cloud` لكن **غير موصول** بإعداد Android فعلي بعد — استدعاءات `ara-ffi` تمرّر `Online` ثابتًا (`TODO(T1.7)` في `core.rs`). الموصول المتبقي: مفتاح إعدادات في Kotlin + تمريره عبر FFI + سجل Privacy Center (ما نُفِّذ ولا نُقَاس ولا نُرسَل) الذي يعرض هذا للمستخدم. تنزيل النماذج (ara-model-manager) غير متأثر عمدًا: التنزيل فعل صريح من المستخدم بالفعل، ليس اتصالًا خلفيًا.

### ADR-016: واجهتا المهام والأمان + WorkManager (T0.3، غير مُختبر على جهاز)
- النواة (`ara-missions`, `ara-sentinel`) وربط FFI (`create_mission`, `missions`, `mission`, `mission_audit`, `set_mission_status`, `resumable_missions`, `run_mission_step`, `decide_mission_approval`, `security_check`) كانوا موجودين ومُختبرين من قبل بدون واجهة. أُضيفت الواجهة فقط؛ منطق الأمان/الميزانية/الموافقات نفسه لم يتغيّر.
- `MissionWorker` (CoroutineWorker): خطوة واحدة محدودة في كل تشغيل (استدعاء موديل واحد محدود، لا حلقة مستمرة في الخلفية)، ثم يعيد جدولة نفسه بـ`WorkManager.enqueueUniqueWork` (REPLACE) لو المهمة لسه `running`، أو يتوقف بصمت لو توقفت/انتهت/محتاجة موافقة (مع إشعار في الحالتين الأخيرتين). عند إغلاق التطبيق أو إعادة تشغيل الهاتف: `MainActivity` يستدعي `resumable_missions` ويعيد جدولة كل مهمة لسه شغالة.
- شاشة الموافقات تستخدم نفس مسار الشات حرفيًا: `decide_mission_approval` → `ToolCall` JSON → `confirm_action` → `Dispatch` → `HostActions.run` لو `run_on_host`. لا مسار تنفيذ مختلف أو أقل تحققًا للمهام.
- `SecurityScreen` يجمع `HostSecurityFacts` من Android APIs العلنية فقط (لا shell، لا استغلال): `ApplicationInfo.FLAG_DEBUGGABLE`، `Settings.Global` لـADB/خيارات المطورين، `KeyguardManager.isDeviceSecure`، `Build.VERSION.SECURITY_PATCH`، `getInstallSourceInfo`، تخمين محاكي من `Build.FINGERPRINT/MODEL/HARDWARE`، ووجود مسارات `su` شائعة. كل حقل اختياري ويُترك غائبًا (لا يُخمَّن) لو فشلت القراءة — يطابق فلسفة `ara_sentinel::HostSecurityFacts` (`#[serde(default)]`).
- **مُختبر:** `./gradlew :app:assembleDebug` و`:app:testDebugUnitTest` (ترجمة Kotlin الفعلية مقابل bindings UniFFI المولَّدة، دمج الموارد والمانيفست). **غير مُختبر:** أي سلوك فعلي على جهاز (استمرار WorkManager بعد إغلاق التطبيق فعليًا، ظهور الإشعار، صحة حقائق الأمان على هاتف حقيقي) — يحتاج T0.2.
- قرار واجهة: 7 تبويبات أسفل الشاشة (أضيف Missions وSecurity) بدل تداخلهم تحت الإعدادات، التزامًا بالنص الحرفي للخطة. ملاحظة صادقة: هذا مزدحم على شاشة هاتف ولم يُختبر بصريًا على جهاز — قد يحتاج مراجعة بعد T0.2.

### ADR-012: API Hub ودرع الخصوصية
- `CloudModel` ينفّذ `LoadedModel` ⇒ نفس المسار للمحلي والسحابي، وواجهة المحادثة تعرض «☁ سحابي» بوضوح.
- https فقط، بلا بيانات اعتماد في الرابط. أخطاء HTTP تُترجم دون أي جزء من المفتاح، و`Debug` لا يطبع المفتاح.
- الموافقة لا تُمنح إلا عبر `set_cloud_consent` (أي `consent` داخل JSON يُتجاهل).
- الدرع مطابقة أنماط (best-effort) ومذكور ذلك للمستخدم في شاشة الموافقة.
