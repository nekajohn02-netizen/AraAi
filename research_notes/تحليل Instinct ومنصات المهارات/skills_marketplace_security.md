# Skills/plugin marketplace security — raw research notes (OpenClaw/ClawHub + academic literature)

**Research date:** 2026-11-25. **Why this matters to ARA:** `docs/ROADMAP_TASKS.md` T2.2 ("Skills Ecosystem: manifest + signing + sandbox + resource limits + revocation") is still an open design. The incidents and papers below are the most concrete, documented record anywhere of what actually goes wrong when an AI agent gets a user-installable "skills" system — i.e. exactly the feature class ARA is planning. This is used as direct input to a new architecture decision (`docs/ARCHITECTURE.md` ADR-017), not as a claim that OpenClaw is a competitor to ARA (it is a general-purpose coding-agent ecosystem, unrelated to on-device Arabic assistants).

**Caveat on numbers:** multiple vendors audited different, overlapping samples of the same marketplace (ClawHub, the skill registry for the OpenClaw agent) at different times with different methodologies. The exact counts below disagree across sources — they are cited as *order-of-magnitude evidence that this failure mode is real and recurring*, not as a single authoritative figure. Do not quote one number as "the" count without naming which audit it came from.

## 1. The ClawHavoc campaign and related audits

- **ClawHavoc campaign:** a coordinated poisoning campaign against ClawHub (OpenClaw's skill marketplace), using compromised publisher accounts. One account (SkillSafe, 2026 post-mortem) puts it at **1,184 malicious skills**, starting 2026-01-27 and surging 2026-01-31, via 12 compromised accounts. ([SkillSafe](https://skillsafe.ai/blog/clawhavoc-post-mortem/), [CyberPress](https://cyberpress.org/clawhavoc-poisons-openclaws-clawhub-with-1184-malicious-skills/))
- **Koi Security audit:** of 2,857 skills scanned, found **341 malicious skills**, grouping 335 under the ClawHavoc name; these used fake "prerequisite" steps to install an Apple macOS infostealer (Atomic Stealer / AMOS). ([The Hacker News](https://thehackernews.com/2026/02/researchers-find-341-malicious-clawhub.html))
- **Palo Alto Networks Unit 42:** found that at least 5 malicious skills bypassed ClawHub's own platform screening (which uses VirusTotal + a tool called ClawScan) and were published successfully despite those controls. ([cybersecuritynews.com](https://cybersecuritynews.com/clawhub-skills-expose-ai-agents/))
- **Snyk ("ToxicSkills" study):** scanned 3,984 skills across ClawHub and a second registry (skills.sh); **36.8% (1,467 skills) carried at least one security issue**, and found prompt injection in roughly a third of the sampled set. ([Snyk](https://snyk.io/blog/toxicskills-malicious-ai-agent-skills-clawhub/))
- **Bitdefender:** counted roughly 900 malicious skills across ~5,000 third-party skills reviewed (~20%).
- **Lakera:** audited 4,310 skills, deep-analyzed 221, tied 44 to the ClawHavoc campaign with ≥12,559 cumulative downloads before removal. Lakera's core technical point: **OpenClaw skills execute with the user's full local privileges and can read environment variables — this alone enables immediate credential harvesting** the moment a malicious skill runs, with no further exploit needed. ([Lakera](https://www.lakera.ai/blog/the-agent-skill-ecosystem-when-ai-extensions-become-a-malware-delivery-channel))
- **Cleanup outcome:** ClawHub's catalog shrank to 3,498 skills after the worst batches were pulled — i.e. even after a large, public cleanup effort, a marketplace of this kind still carries real risk at scale.

## 2. Why the sandbox/moderation layer failed (the structural lessons, not just the incident count)

- **Sandboxing was optional, not mandatory, and defaulted to off in practice.** Certik: OpenClaw's own documentation states Docker-based sandboxing is optional; when it's off, host tools stay fully reachable. Certik's broader point: *"a sandbox that is difficult to use, requires repeated confirmation, or breaks too many common skill behaviours tends not to become the default in practice"* — i.e. an opt-in security boundary gets opted out of. ([Certik](https://www.certik.com/blog/skill-scanning-is-not-a-security-boundary))
- **The enforcement path itself had bugs, not just a missing feature.** Snyk Labs documented a real bypass: a policy-merge failure in the `/tools/invoke` path meant the sandbox policy that was configured was never actually merged into the policy applied at runtime. Snyk also found a TOCTOU (time-of-check-to-time-of-use) race condition in sandbox path validation, and reported both upstream. ([Snyk Labs](https://labs.snyk.io/resources/bypass-openclaw-security-sandbox/))
- **Moderation was faster than malware scanning, and approval wasn't permanent.** Researchers found OpenClaw's own approval/moderation step was fast, while the VirusTotal check that was supposed to catch malware sometimes took *days* to flag an addition — a window attackers used. Worse: **skills could be modified after approval to add an exploit**, i.e. passing review once was not a durable guarantee. (Multiple sources, summarized by [1Password](https://1password.com/blog/from-magic-to-malware-how-openclaws-agent-skills-become-an-attack-surface) and the Semgrep cheat sheet)
- **The content model itself is the attack surface, independent of any sandbox bug.** 1Password's framing: a "skill" in this ecosystem is essentially markdown text with no restriction on what instructions/commands it contains — it can carry copy-paste-able terminal commands as plain instructions. Their recommendation: *assume skills will be weaponized*, because the format gives no structural reason they can't be. ([1Password](https://1password.com/blog/from-magic-to-malware-how-openclaws-agent-skills-become-an-attack-surface))
- **Academic taxonomy — general framework critique, not OpenClaw-specific:** an arXiv paper (Texas A&M SUCCESS Lab, cataloguing 190 OpenClaw security advisories) argues the general "agent skills" framework pattern treats a skill's instructions as *operator-level directives* (i.e. trusted, elevated text, not data), grants persistent permissions from a *single* approval (no per-use re-check), imposes *no mandatory security review* before distribution, and lets bundled scripts execute with the *user's own local privileges* (no privilege separation at all). The paper notes the project's rapid growth made it a high-visibility target before its disclosure process had matured. ([arXiv:2603.27517](https://arxiv.org/pdf/2603.27517))
- **A proposed fix in the literature:** SkillGuard (2026) proposes a "permission-centric framework" for agent-skill security — i.e. the field's own research consensus is converging on exactly the capability/permission model ARA's tool system (`docs/ARCHITECTURE.md` ADR-006) already implements for its built-in tools. ([SkillGuard, arXiv:2606.03024](https://www.alphaxiv.org/abs/2606.03024))

## 3. The one real-world counter-example found: Google AI Edge Gallery's Agent Skills

(This is the competitor already covered in `docs/COMPETITIVE_ANALYSIS.md` §2.4 — noted here only for its skills-permission mechanism, which is the one concrete prior-art example of doing this *better*.)

- Third-party developer write-ups (not an official Google security audit — treat as 🟡/⚪) describe Edge Gallery's Agent Skills as working like scoped micro-apps: if a skill tries to read the device calendar without having declared `calendar.read`, the on-device runtime (LiteRT-LM) intercepts and blocks the call outright, rather than the skill's own code enforcing it. Calendar read and calendar write are modelled as *separate* declared capabilities with separate toggles. ([dev.to walkthrough](https://dev.to/parulmalhotraiitk/building-offline-brain-how-i-wrote-my-first-custom-agent-skill-for-android-google-io-2026-1m43))
- Scope limit noted in the same source: only Gemma-family models currently run Agent Skills in Gallery, i.e. the feature isn't universal across their own model catalog either.
- No official Google security write-up specific to Edge Gallery's skills was found; Google's general "Gemini defense-in-depth" post describes dedicated security reviews and an external vulnerability-reward program for Gemini broadly, but doesn't name Edge Gallery. ([Google Safety & Security blog](https://blog.google/security/how-geminis-defense-in-depth-approach-works/))

## Bottom line for ARA's T2.2 design

Every structural failure above traces to one of two root causes: (a) skills are **executable code** (scripts) running with **ambient, unscoped privilege** (env vars, host tools, local user permissions), or (b) a skill's **instructions are trusted as directives** rather than treated as untrusted content, and permission is granted **once, persistently, from a single approval** with no re-verification at use-time or after an update. ARA's existing `core/crates/ara-tools/src/skills.rs` already avoids both root causes *by construction*, not by a bolt-on sandbox: a `SkillManifest` is declarative data (id/instructions/tool-id-list only — no executable payload, no new primitive), its `instructions` field is explicitly documented in-code as something that "can never widen the permissions of a tool," and every tool it can request already goes through the existing mandatory-confirmation-for-external-effect `dispatch()` gate (`docs/ARCHITECTURE.md` ADR-006), proven under adversarial content in T1.9. The open design work for T2.2 is therefore narrower than the OpenClaw case: signing/distribution/revocation plumbing on top of guarantees that are already built and already tested — not a sandbox to invent from scratch. See `docs/ARCHITECTURE.md` ADR-017 for the resulting design.
